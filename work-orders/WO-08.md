# WO-08 — Interface on the live API

## Summary

Replace the superseded offline-leaderboard work order with the web application
specified in AGENTS.md and the owner's November 14 implementation request.
Build `web/` with React, Vite and TypeScript after WO-09 provides the API.
The seven boards in `docs/mockup/` are the authority for layout and visual style;
their invented research results are not application data.

## Acceptance Criteria

- Run, Leaderboard, Tearsheet, Graveyard, New run, Evals and Data follow the
  corresponding boards and shared header navigation.
- Extract the board colours, typography and spacing into one tokens file.
  Use the dark background, serif headings and monospace labels shown. Share
  status pills, eval dots, pipelines, variant cards, spec panels, data-need rows
  and log lists instead of rebuilding them per screen.
- A single data-access module calls `/api`. All displayed research names,
  numbers, statuses, counts, plots and narratives come from real API records.
  Empty, extraction-failed, inactive, unresolved, all-failed and void states
  are explicit. Voided runs are excluded by default with an explicit audit view.
- Show `test_type` and evals passed n/5 wherever a variant result appears.
  Reserve positive result styling for VERIFIED. Keep limitations, including
  survivorship bias, visible. Model narratives are labelled narrative-only;
  authoritative status/metric summaries come from deterministic API templates.
- Run overview and variant tabs expose ordered steps, details and the recorded
  log lines for each step, including bounded bug repairs.
- Tearsheet shows recorded gross/net equity, IS/OOS boundaries, all evals,
  strategy code, heal history and the linked structured graveyard entry.
- Data exposes actual catalog/preview/coverage/gaps/fills, ingest history,
  contract field descriptions and the artifact inventory. Reserved HOLDOUT
  values are not exposed as strategy or model inputs.
- Evals shows the five existing evaluations and their actual read-only rules.
  Do not invent draft evals or fixture results shown in the mock-up.
- Missing backend capabilities (spec editing, described strategies, provider
  keys, event uploads, threshold sliders and draft-eval controls) remain visible
  where drawn, disabled, and labelled "not available yet". PDF intake works.
- Uploading a PDF starts a real run, navigates to its Run screen and follows
  replayable server-sent events through completion. Leaving and reopening a
  run preserves its progress through the API.
- Open all seven screens against the existing records, exercise all eight
  historical runs including the explicit void view, and save screenshots under
  `report/`. Start one new paper from the UI and follow it to completion.
- Run the full test suite and frontend checks; report every intentional visual
  difference from the boards. Commit at the phase checkpoints.

## Phase 3 acceptance

Phase 3 accepted: seven screens implemented; 15 frontend tests, production build,
formatting and the real-browser read-only gate passed. Every historical run,
pipeline detail, explicit void audit, artifact preview and mobile layout was
checked. See [interface report](../docs/INTERFACE.md). The real submitted run and
final suite/screenshot evidence are the separate Phase 4 gate.

## Out of Scope

No fabricated research data, financial tuning, changes to strategy contracts or
eval logic/configuration, trade execution, auth, multi-user hosting, deployment,
described-strategy implementation, provider-key writes, event ingestion or
editable eval thresholds. Future controls do not acquire fake behavior.
